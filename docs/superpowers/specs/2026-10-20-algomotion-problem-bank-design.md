## 1. 왜 바꾸나

AlgoMotion은 프로그래머스 Lv 2~3 문제의 풀이를 한 단계씩 움직이는 그림, 실행 중인 코드 줄, 변수 값으로 보여 주는 코딩테스트 학습 앱입니다. 지금은 4문제뿐이고, 문제마다 정석·대안·함정 풀이 3가지를 코드로 비교하지만 그림은 정석 풀이에만 있습니다.

사용자에게 가장 도움이 된 것은 "알고리즘이 어떤 식으로 돌아가는지 시각화로 볼 수 있다"는 점입니다. 아쉬운 점은 두 가지였습니다.

1. 문제가 너무 적고 알고리즘별로 나뉘어 있지 않습니다.
2. 움직임이 "모션 그래픽이 아니라 틱 단위 영상 같아서" 부드럽지 않습니다. 단계가 바뀌면 그림이 한 번에 뚝 바뀝니다. 첫 개선 시안(작은 효과를 많이 넣은 판)에는 "좀 더 이해하기 쉽게, 지금은 자잘하다"는 반응이었습니다.

## 2. 이렇게 되면 성공

- 앱을 열면 알고리즘 유형별로 문제가 보이고, 자주 나오는 유형일수록 문제가 많습니다.
- 문제를 열면 정석·대안·함정 세 풀이가 **각각** 움직이는 그림으로 돌아가고, 탭으로 바꿔 보거나 나란히 경주시켜 비교할 수 있습니다.
- 그림은 단계 사이가 끊기지 않고 이어지며, 한 단계 안에서도 "지금 무슨 일을 하는지"가 큰 글씨와 순서로 또렷하게 보입니다.
- 코드 줄 하이라이트, 변수, 자막이 그림과 정확히 맞습니다.

## 3. 목표, 하지 않을 것, 실패로 보는 것

### 목표
1. 움직임 엔진을 새로 만듭니다. 한 단계를 이름 붙은 마디(예: 꺼내기 → 살피기 → 넣기)로 나눠 차례로 움직입니다(4.1).
2. 모든 문제의 세 풀이 모두에 시각화를 붙입니다. 탭으로 하나씩 크게 보고, '나란히 비교'로 동시에 경주시킵니다(4.2).
3. 홈 목록과 문제 화면 옆 메뉴로 76문제를 유형별로 고릅니다(4.3).
4. 문제를 76개로 늘립니다(4.4).
5. `npm run check`가 모든 문제의 코드(JavaScript와 Python), 하이라이트 줄, 그림의 답을 자동으로 확인합니다(6.5).

### 하지 않을 것
- 로그인, 서버, 사용자 코드 실행(온라인 채점)은 만들지 않습니다.
- '구현/시뮬레이션'은 따로 유형으로 두지 않습니다. 자주 나오지만 특정 알고리즘이 아니기 때문입니다.
- Lv 1, Lv 4 이상 문제는 넣지 않습니다.
- 다크 모드와 다국어는 만들지 않습니다(지금 앱도 밝은 연습장 한 가지 모습입니다).
- 프로그래머스 문제 지문을 그대로 옮기지 않습니다. 지금처럼 우리 말로 요약하고 원문 링크를 답니다. 입출력 예는 원문 그대로 씁니다.

### 실패로 보는 것 (돌아가더라도)
- 작은 효과가 여기저기서 동시에 터져 산만한 그림. 사용자가 "자잘하다"고 한 판이 기준입니다.
- 단계마다 그림이 통째로 바뀌는 슬라이드 같은 느낌.
- 그림, 자막, 코드 줄, 변수가 서로 어긋나는 것.
- 틀린 풀이 코드나 틀린 답, 어색한 조사(예: "(1,0)를").

## 4. 사용자가 시안을 보고 정한 것

### 4.1 움직임: 시안 ① 수정안
시안 ① 2번째 판을 그대로 따릅니다.

- **마디 표시줄**: 한 단계를 이름 붙은 마디로 나누고(BFS라면 ① 꺼내기 ② 살피기 ③ 넣기), 화면 위쪽에 지금 마디를 형광펜으로 표시합니다. 마디 이름은 풀이마다 정하고, 한 풀이 안에서는 같은 이름 묶음을 씁니다.
- **크게**: 격자 칸 54px 안팎, 칸 숫자 18px, 자막 16px. 무대를 작은 화면 여러 개로 쪼개지 않습니다.
- **차례로**: 마디 안의 일도 한 번에 하나씩 일어납니다. 큐에서 꺼낸 칸이 격자로 날아가고, 상하좌우를 하나씩 확인하고, 새 칸이 큐 뒤로 날아 들어가는 식입니다.
- **스포트라이트**: 살피는 마디에서는 상관없는 칸을 흐리게 둡니다.
- **화살표와 판정 표시**: 이웃을 확인할 때 작은 점 대신 화살표를 긋고, 대상에 '벽', '방문함', '새 칸' 같은 판정 표시를 붙입니다.
- **자잘한 효과 금지**: 흔들림, +1 떠오르기, 작은 점 같은 효과는 쓰지 않습니다.
- **끊기지 않는 진행 막대**: 막대가 단계 사이에 뛰지 않고 단계 안에서도 흘러갑니다.
- **조작**: 재생/멈춤, 이전/다음 단계, 처음으로, 속도. '다음'은 다음 단계를 한 번 움직여 보여 주고, '이전'과 타임라인 끌기는 해당 단계가 끝난 모습으로 바로 갑니다.

### 4.2 세 풀이 보기: 탭이 기본, '나란히 비교'는 버튼으로
시안 ②의 A안을 기본으로 하고 B안을 버튼으로 엽니다.

- **탭(기본)**: 문제 화면에서 `○ 정석 · BFS`, `△ 대안 · 다익스트라`, `✕ 함정 · DFS` 탭으로 풀이를 바꿉니다. 탭을 바꾸면 그림, 마디 표시줄, 자막, 코드, 변수가 그 풀이 것으로 바뀝니다. 한 번에 하나만 크게 봅니다.
- **나란히 비교(버튼)**: 세 풀이를 작은 판 세 개로 같은 박자에 동시에 돌립니다. 판마다 '한 일의 양' 계수기와 끝났을 때 '끝!' 도장을 보여 줍니다. 단계가 많은 풀이는 계속 돌아갑니다. 좁은 화면에서는 세 판을 위아래로 쌓습니다.
- **한눈에 비교 막대**: 세 풀이가 한 일의 양을 막대로 비교합니다. 단위는 문제마다 하나로 정합니다(예: 게임 맵은 '칸을 밟은 횟수', 정석 16번 · 대안 16번 + 힙 정렬 32번 · 함정 25번).

### 4.3 문제 고르기: 홈 목록 + 문제 화면 옆 메뉴
시안 ③의 A안과 B안을 섞습니다.

- **홈**: 출제 빈도 3단계(아주 자주 / 자주 / 가끔) 아래에 유형 카드를 놓습니다. 카드에는 유형 이름, 핵심 발상 한 줄, 문제 수, 본 문제 수와 진행 막대, 문제 목록(레벨, 제목, 정석 풀이 이름, 본 표시)이 있고 5개를 넘으면 '더 보기'로 펼칩니다. 위쪽에 검색(제목·유형·정석 풀이 이름)과 '이어 보기'(마지막으로 본 문제)가 있습니다. 카드가 한 줄에 혼자 남지 않도록 유형 수로 나누어떨어지는 열 수만 씁니다.
- **문제 화면 옆 메뉴**: 왼쪽에 빈도 단계 → 유형 → 문제 순의 목록이 붙어 있고 지금 문제가 표시됩니다. 위에 '빈도 › 유형 › n/전체' 경로와 같은 유형 안의 이전/다음 문제 버튼이 있습니다. 좁은 화면에서는 '문제 목록' 버튼으로 엽니다.

## 5. 제가 정한 것 (검토 부탁)

사용자가 따로 정하지 않았지만 만들기 전에 정해 둬야 하는 것들입니다. 바꾸고 싶으면 말씀해 주세요.

1. **문제 화면 배치**: 넓은 화면(1280px 이상)은 [옆 메뉴 240px, 접을 수 있음] [가운데: 문제 머리 → 풀이 탭과 '나란히 비교' 버튼 → 재생 화면 → 고른 풀이의 평가(이유, 좋은 점, 아쉬운 점) → 한눈에 비교 막대] [오른쪽 380px 안팎: 코드, 변수, 복잡도] 세 칸입니다. 문제 머리에는 제목, 레벨, 유형, 원문 링크와 함께 '문제 보기'를 펼치면 요약, 제한 사항, 입출력 예, 핵심 발상이 나옵니다. 지금처럼 넓은 화면에서는 한 화면에 고정하고 칸마다 따로 스크롤합니다. 중간 폭(900~1279px)에서는 옆 메뉴가 서랍으로 바뀌고, 좁은 화면(900px 미만)은 한 줄로 쌓습니다.
2. **'풀이 비교' 화면은 없앱니다.** 그 내용(평가, 좋은 점·아쉬운 점, 코드, 비교표)은 문제 화면의 풀이 탭과 비교 막대로 옮깁니다. 헤더의 '모션 학습 / 풀이 비교' 전환도 없어집니다. '사용법' 창은 새 화면에 맞게 고쳐서 남깁니다.
3. **주소**: 홈은 `#/`, 문제는 `#/p/<문제 id>`인 해시 주소를 씁니다. 브라우저 뒤로 가기와 링크 공유가 됩니다. 라우터 라이브러리는 쓰지 않습니다.
4. **본 문제와 이어 보기**: 정석 풀이를 마지막 단계까지 보면 그 문제를 '봤음'으로 표시하고, 마지막으로 연 문제를 '이어 보기'에 씁니다. 둘 다 브라우저 저장소(localStorage)에 두고, 읽고 쓸 때 실패해도 앱은 정상으로 돌아갑니다.
5. **재생 기본값**: 문제를 열면 멈춘 상태로 첫 단계를 보여 줍니다(지금과 같음). 속도는 0.5×, 1×, 1.5×, 2×입니다. 1×에서 마디 하나는 0.5~1초, 단계 하나는 보통 2~3.5초입니다. 마지막 결과 단계는 더 오래 보여 줍니다. 단축키(Space, ←, →, R)는 그대로 둡니다. 끝났을 때 색종이 효과는 정석 풀이에서만 씁니다.
6. **시각화 입력은 문제마다 하나**: 세 풀이가 같은 입력으로 돌아갑니다. 그래서 탭을 바꿔도, 나란히 비교에서도, 비교 막대에서도 같은 입력을 놓고 비교합니다. 입력은 정석을 보여 주기 좋으면서 함정도 드러나도록 고릅니다. 오답이 나는 함정이면 오답이 드러나는 가장 작은 입력을 씁니다(기능개발이라면 남은 날이 `[5, 3, 4]`가 되는 `progresses = [95, 97, 96], speeds = [1, 1, 1]`처럼). 시간 초과가 나는 함정이면 작은 입력에서 '한 일의 양'이 정석보다 크게 늘어나는 모습을 보여 주고, 마지막 자막에서 최대 입력이면 몇 번이 되는지 짚어 줍니다. 시각화 입력은 원문 입출력 예와 다를 수 있으므로 재생 화면에 입력을 표시합니다.
7. **한 일의 양 단위**: 문제마다 단위 하나(`workUnit`, 예: '칸을 밟은 횟수', '검사 횟수', '확인한 경우의 수')를 정하고 세 풀이가 같은 단위로 셉니다. 필요한 풀이는 덧붙임 한 줄을 둘 수 있습니다(예: '+ 힙 정렬 32번').
8. **'나란히 비교'의 움직임은 단순하게**: 작은 판 세 개에서 마디 연출까지 돌리면 사용자가 싫어한 '자잘한' 화면이 됩니다. 그래서 비교 모드는 단계가 끝난 모습 사이를 부드럽게 잇는 정도로만 움직입니다(시안 ②의 B안 수준).
9. **새 라이브러리는 넣지 않습니다.** 움직임은 Web Animations API와 CSS 전환으로 만듭니다(시안이 이 방식으로 만들어졌습니다).
10. **Python 코드도 점검합니다.** 이 컴퓨터에 python3(3.14)가 있으니 `npm run check`가 Python 풀이도 실행해 확인합니다. python3가 없으면 Python 점검만 건너뛰고 그 사실을 출력합니다.
11. **오래 걸리는 시각화는 줄입니다.** 정석 풀이의 시각화는 8~25단계 안팎이 되도록 예제를 고르거나 줄이고, 함정은 40단계를 넘지 않게 합니다. 같은 일이 많이 반복되면 '빨리 감기' 마디 하나로 묶고 계수기만 올립니다.

## 6. 만드는 방식

### 6.1 데이터 모델 (윤곽)
정확한 이름과 모양은 만드는 사람이 정합니다. 바뀌는 핵심은 세 가지입니다. 시각화가 문제가 아니라 **풀이마다** 붙고, 한 단계가 **마디**로 나뉘고, 단계마다 **끝난 모습(장면)** 을 함께 가집니다.

```ts
type CategoryId = 'dfs-bfs' | 'brute-force' | 'dp' | 'greedy' | 'hash' | 'stack-queue'
  | 'binary-search' | 'sort' | 'heap' | 'graph' | 'two-pointer';

interface Category { id: CategoryId; name: string; tier: 1 | 2 | 3; idea: string; problems: ProblemMeta[] }
// 홈과 옆 메뉴는 이 가벼운 정보만으로 그립니다. 문제 본문은 열 때 불러옵니다.
interface ProblemMeta { id: string; title: string; level: 2 | 3; bestName: string; load: () => Promise<Problem> }

interface Problem {
  id: string; title: string; level: 2 | 3; category: CategoryId; sourceUrl: string;
  description: { summary: string; rules: string[]; examples: { input: string; output: string }[] };
  keyIntuitions: string[];
  demo: { input: unknown[]; label: string };     // 세 풀이가 함께 쓰는 시각화 입력 (5-6)
  workUnit: string;                              // 세 풀이가 한 일을 세는 같은 단위
  approaches: [Approach, Approach, Approach];    // 정석, 대안, 함정 순서
}

interface Approach {
  id: string; name: string; rank: 'BEST' | 'ALTERNATIVE' | 'TRAP';
  timeComplexity: string; spaceComplexity: string;
  verdict: string; pros: string[]; cons: string[]; whyThisRank: string;
  code: Record<'python' | 'javascript', string>;
  generateSteps: () => AlgorithmStep[];          // 문제의 demo.input으로 돌린 단계들
}

interface AlgorithmStep {
  title: string;
  phases: Phase[];          // 이 단계를 움직이는 마디들 (1개 이상)
  scene: Scene;             // 이 단계가 끝난 모습. 이전/다음/타임라인/나란히 비교는 이것만 씁니다
  codeHighlights: Record<'python' | 'javascript', number[]>;
  variables: Record<string, string | number>;
  work: number;             // 지금까지 한 일의 양 (workUnit 단위)
  workNote?: string;        // 예: '힙 정렬 32번'
  answer?: unknown;         // 마지막 단계에만. 점검 스크립트가 확인합니다
  isKeyframe?: boolean;
}

interface Phase {
  label: string;            // 마디 표시줄의 이름. 예: '꺼내기'
  caption: string;          // 이 마디의 자막
  actions: Action[];        // 무대에 차례로 일어나는 일
  codeHighlights?: Record<'python' | 'javascript', number[]>;  // 마디마다 코드 줄을 바꿀 때만
}
```

### 6.2 움직임 엔진
- 단계 `k`를 재생하면 엔진이 단계 `k-1`의 장면에서 시작해 마디를 차례로 연출하고, 끝나면 단계 `k`의 장면으로 정확히 맞춥니다. 연출이 조금 어긋나도 단계가 끝날 때 바로잡힙니다.
- 마디의 `actions`는 무대 부품이 해석하는 선언형 명령입니다. 예: 스포트라이트(대상 외 흐리게), 토큰 날리기(큐 → 칸, 칸 → 스택), 상태 칠하기, 화살표 + 판정 표시, 숫자 띄우기, 포인터 옮기기, 두 칸 바꾸기, 경로 그리기, 빨리 감기(계수기만 올림). 명령의 정확한 목록은 만드는 사람이 정하되, 4.1의 규칙(한 번에 하나, 큰 글씨, 자잘한 효과 금지)을 엔진이 기본으로 지키게 합니다.
- '이전', 타임라인 끌기, 탭 바꾸기는 연출 없이 장면만 바꿉니다. 재생 중에 이런 조작이 들어오면 진행 중인 연출을 멈추고 장면을 맞춥니다.
- 움직임 줄이기(`prefers-reduced-motion`) 설정이면 날아가기 같은 이동 없이 짧게 바뀌는 것만 보여 줍니다.
- 진행 막대는 단계 안에서도 시간에 따라 흐릅니다.

### 6.5 점검 스크립트 (`npm run check`)
문제마다, 풀이마다 다음을 확인하고, 하나라도 어긋나면 어느 문제의 어느 풀이인지 알려 주며 실패합니다.

1. 모든 단계와 마디의 하이라이트 줄이 그 풀이 코드 안에 있습니다(지금처럼 `at(code, '코드 일부')`로 지정).
2. 마지막 단계에 `answer`가 있고, 문제의 시각화 입력을 그 풀이의 JavaScript 코드로 돌린 결과와 같습니다.
3. 정석과 대안의 JavaScript·Python 코드가 모든 입출력 예와 문제별 추가 사례를 맞힙니다.
4. 정석과 대안의 답이 작은 무작위 입력에서도 서로 같습니다. 문제마다 시드를 고정한 작은 입력 생성기를 둡니다.
5. 함정은 함정임이 드러납니다. 오답형은 시각화 입력에서 함정의 답이 정석과 다르고, 시간 초과형은 시각화 입력에서 함정의 `work`가 정석보다 큽니다.
6. 단계마다 마디가 1개 이상이고 자막이 비어 있지 않으며, `work`가 줄어들지 않습니다.
7. 목록과 문제 파일이 맞습니다. 문제 id가 겹치지 않고, 유형별 문제 수가 10/6/4입니다.

## 7. 문제 하나의 완성 기준

- 제목, 레벨, 번호를 원문에서 확인했습니다.
- 요약과 제한 사항은 우리 말로 새로 썼고, 입출력 예는 원문과 같습니다. 핵심 발상 3줄이 있습니다.
- 정석·대안·함정 세 풀이마다 이름, 시간·공간 복잡도, 한 줄 평, 좋은 점, 아쉬운 점, 평가 이유가 있고, 같은 알고리즘을 Python과 JavaScript로 씁니다. JavaScript 큐는 `shift()` 대신 머리 인덱스를 쓰는 등 지금 코드의 습관을 따릅니다.
- 세 풀이 모두 시각화가 있습니다. 마디 이름이 일관되고, 자막은 자연스러운 우리말에 조사가 맞습니다(숫자 뒤 조사는 `josa`, `ro` 도구). 한 일의 양을 셉니다.
- 함정 풀이의 마지막 단계는 왜 함정인지 분명히 보여 줍니다(오답을 정답과 나란히, 또는 일의 양이 폭발하는 모습과 최대 입력에서의 횟수).
- `npm run check`를 통과하고, 브라우저에서 넓은 화면과 휴대폰 폭으로 겹치거나 잘리는 곳이 없는지 확인했습니다.

## 8. 만드는 순서

이 설계는 전체를 다루지만 구현 계획은 단계마다 따로 씁니다. 단계가 끝날 때마다 점검을 통과시키고 사용자가 브라우저에서 확인합니다.

1. **엔진과 화면**: 새 데이터 모델, 움직임 엔진, 무대 부품(격자, 수직선, 줄, 삼각형), 홈·옆 메뉴·주소, 풀이 탭·나란히 비교·비교 막대, 새 점검 스크립트. 지금 있는 4문제를 새 모델로 옮기고 세 풀이 모두에 시각화를 붙입니다(시각화 12개). **여기서 사용자가 움직임과 화면을 실제 앱으로 확인합니다.**
2. **아주 자주 나오는 유형**: DFS/BFS, 완전탐색, DP, 그리디의 새 문제 38개. 필요한 무대 부품(나무, 그래프, 배열, 행렬 표)을 이때 만듭니다.
3. **자주 나오는 유형**: 해시, 스택/큐, 이분 탐색, 정렬의 새 문제 22개.
4. **가끔 나오는 유형**: 힙, 그래프, 투 포인터의 새 문제 12개.

2~4단계는 유형별로 나눠 여러 작업자가 동시에 만들 수 있습니다. 문제 파일이 서로 겹치지 않고, 새 무대 부품만 먼저 만들어 두면 됩니다.

## 9. 만드는 사람에게 맡기는 것

- 타입, 컴포넌트, 엔진 명령의 정확한 이름과 모양.
- 무대 부품의 구체적인 모양과 부품을 어떻게 나눌지.
- 문제마다 대안·함정 풀이로 무엇을 고를지. 대안은 '맞지만 손해를 보거나 덜 일반적인 풀이', 함정은 '자주 떠올리지만 오답이나 시간 초과로 이어지는 풀이'이고, 6.5의 5번으로 드러나야 합니다.
- 문제마다 시각화 입력(5-6의 기준을 따름), 마디 이름, 한 일의 양 단위.
- 홈과 옆 메뉴의 세부 시각 디자인(시안 ③의 구조를 따름).
- 문제 파일을 불러오는 단위(문제별 또는 유형별 묶음).
